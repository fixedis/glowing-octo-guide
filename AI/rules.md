# Жёсткие правила проекта

---

## Архитектура

1. CoreEngine — только инфраструктура.
2. Игровые домены находятся в подключаемых движках.
3. Движки не должны знать внутренности друг друга.
4. Все межмодульные взаимодействия идут через ядро.
5. Сущности движков отделены от ядер движков.
6. Новые сущности не должны требовать изменения ядра движка.
7. Манифест описывает движок.
8. Зависимости движков задаются через `requires` и `provides`.

---

## Код

1. PHP 8.1.
2. `declare(strict_types=1);` обязателен.
3. Интерфейсы используются для абстракций.
4. Dependency Injection через конструкторы.
5. Readonly свойства используются там, где это возможно.
6. Каждый класс должен иметь одну ответственность.
7. Не создавать лишние файлы без необходимости.
8. Не создавать файлы под каждый игровой экземпляр.
9. Все ошибки должны быть логируемыми и локализуемыми.
10. Все критичные механизмы должны иметь тесты.

---

## Числа

1. Критичная симуляция не использует float.
2. Используется integer или fixed point.
3. Округление должно быть явным.
4. Деление должно использовать масштаб.
5. Все случайные источники должны быть детерминированными.
6. Запрещены `rand()` и `mt_rand()`.
7. Движок использует детерминированный RNG. Собственный RNG движка допустим ТОЛЬКО при обоснованной синхронизации с клиентом (как `SeedGraph` в UniverseEngine, побайтово совпадающий с TS-реализацией). В остальных случаях используется `DeterministicRandomInterface` ядра.
8. Используется `MathKernelInterface`.

---

## UI и настройки (зона клиента)

1. Главное меню, интерфейс, экраны и визуализация — зона Vite/TS-клиента (папка `client/`), а не PHP-движков.
2. Клиент общается с бэкендом только через `/api` (команды в `CommandBus`).
3. Настройки делятся на две группы:
   - Игровые (seed, параметры генерации, лимиты бюджета) — через команды в `State`/снапшоты бэкенда.
   - Клиентские (громкость, язык, quality графики, keybindings) — только в клиенте (localStorage/стор), в бэкенд не ходят.
4. UI-логику не следует писать внутрь PHP-движков (нарушение разделения ответственности).
5. `UIEngine` как отдельный модуль пока не создан; его роль исполняет клиент.

## Сеть и HTTP-слой

1. ~~`UniverseEngine/Presentation/` (UniverseRouter + HttpRequest) — техдолг: встроенный REST-адаптер внутри движка.~~ **ЗАКРЫТО:** HTTP-слой вынесен в `NetworkEngine` (`NetworkRouter`), единый фасад `/api/v1/*` для всех движков. `UniverseRouter` помечен DEPRECATED (см. `Docs/Engines/UniverseEngine.md`).
2. `NetworkEngine` — единственный владелец HTTP-маршрутизации; движки не содержат HTTP-адаптеров.
3. Router не должен менять state напрямую — только диспатчить команды через `CommandBus`.

---

## Движки

1. Движок должен иметь манифест.
2. Движок должен реализовывать `EngineInterface`.
3. Если движок регистрирует механизмы, он реализует `RegistrableEngineInterface`.
4. Движок не должен напрямую менять чужое состояние.
5. Движок не должен использовать сеть или базу данных напрямую.
6. Движок должен использовать сервисы CoreEngine.
7. Движок должен быть тестируемым.

---

## Сущности

1. Сущности лежат в папке `Entities` движка.
2. Сущности реализуют интерфейс, указанный в манифесте.
3. Сущности не должны менять ядро движка.
4. Сущности не должны быть игровыми экземплярами.
5. Экземпляры игровых объектов являются данными, а не файлами.

---

## Документация

1. Документация должна отражать реальную архитектуру.
2. Нельзя описывать механизмы, которых ещё нет, как готовые.
3. Изменения архитектуры должны сопровождаться обновлением документации.
4. AI-контекст должен быть синхронизирован с документацией.
